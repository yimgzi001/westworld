## 环境与构建

- 需要 .NET 10 SDK 和 Windows x64 运行环境。构建前确认 `dotnet --list-sdks` 能列出 10.x；只有运行时不能编译源码。
- 首次构建需要恢复 NuGet 包，源配置在 [game/nuget.config](../../game/nuget.config)。
- 先构建单个 Windows 项目，避免整套解决方案同时要求其他平台的工作负载。

```powershell
dotnet --list-sdks
dotnet build game/Survivalcraft.Windows/Survivalcraft.Windows.csproj --configuration Release
```

构建链由 [Survivalcraft.Windows.csproj](../../game/Survivalcraft.Windows/Survivalcraft.Windows.csproj)、[EntitySystem.Windows.csproj](../../game/EntitySystem.Windows/EntitySystem.Windows.csproj) 和 [Engine.Windows.csproj](../../game/Engine.Windows/Engine.Windows.csproj) 组成。[Windows.props](../../game/build/Windows.props) 指定 `net10.0-windows` / `win-x64`，共享选项在 [Common.props](../../game/build/Common.props)。

游戏项目构建前把 `game/Survivalcraft/Content/` 压缩成 `Content.zip`，再将资源包、`init.js` 和运行依赖复制到输出目录。Release 默认输出目录为：

```text
game/Survivalcraft.Windows/bin/Release/net10.0-windows/win-x64/
```

若修改了输出属性，以 MSBuild 实际结果为准：

```powershell
dotnet msbuild game/Survivalcraft.Windows/Survivalcraft.Windows.csproj -nologo -p:Configuration=Release -getProperty:TargetDir
```

### ImageSharp 构建警告

游戏依赖 ImageSharp 3.1.12。该版本的 TIFF 解码存在越界写漏洞，NuGet 会报 `NU1903`。游戏自带的图像、纹理、窗口图标和社区图片读取统一采用[引擎解码配置](../../game/Engine/Engine.Media/Image.cs)，暂时禁用 TIFF 输入。自行调用 ImageSharp 的第三方模组不受此配置约束。[漏洞公告](https://github.com/advisories/GHSA-v76p-62qx-wwq2)

3.2.0 修复了此漏洞。本机试装时因缺少 Six Labors 构建许可证失败。获得许可证后，通过未版本化的 `SixLaborsLicenseFile` 或 `SixLaborsLicenseKey` 配置升级，并重新验证图片读取和 NuGet 审计结果。[官方许可说明](https://sixlabors.com/posts/security-support-and-license-enforcement/)

## 启动当前构建

仓库测试默认静音、隐藏游戏窗口。通用启动器设置 `WENMING_TEST_BACKGROUND=1` 和 `WENMING_TEST_MUTE=1`，引擎创建不可见窗口，游戏音效与音乐音量返回零，后台仍推进真实游戏与模型调用。用户明确要求其他方式时，宿主可向 `Invoke-GameSmoke` 传入 `-Visible`、`-WithSound`，或在测试环境中显式设置对应变量为 `0`。测试结果记录或检查实际窗口可见性和音量。

构建成功后运行：

```powershell
dotnet run --project game/Survivalcraft.Windows/Survivalcraft.Windows.csproj --configuration Release --no-build
```

也可在输出目录运行 `Survivalcraft.exe` 或随附的 `Launch Game 启动游戏.bat`。后者会检查 .NET Desktop Runtime 并显示日志。以所运行的输出目录辨认测试对象，本机下载目录中的发行版和 `source-build/` 属于另外的副本。

## 西部世界开局与飞行

在游戏中进入「开始游戏 → 新建世界」，选「生存」并填写名称和种子，点击「西部世界 · 50 AI」。等本机玩家出生后，游戏在附近选取干燥地面生成 25 男、25 女和有限的开局物资。开局完成时，游戏日志的 `Westworld initial archive` 一行给出 `doc/Westworld/<运行标识>/initial.scworld` 的完整路径。若种子附近找不到足够的干燥地面，日志会记录失败原因，可换一个种子创建新世界。

保存好这份 `initial.scworld`。从主菜单进入「内容 → 设备」，选中归档后回到世界列表打开。每次导入都会创建一份独立世界，恢复同一批成员、人物档案、位置、库存、饱食度和营地区块。要继续已经运行的世界，使用[普通存档恢复](#西部世界普通存档恢复)。

在这种生存世界里，开局创建的本机玩家默认按 `F` 开关飞行，`WASD` 移动，`Space` 上升，`Shift` 下降。按键可在游戏里改。其他玩家和 AI 没有这项飞行权限。营地和远离营地的存活 AI 按活动位置维持地形区块，玩家可以飞出自己的视距再返回。

开局和导入可以离线完成。要启用模型，启动游戏前按[模型配置](#大模型适配层)设置供应商参数，再配置[跨实验额度](#跨实验额度与自动暂停)。

实机回归使用两个独立进程依次运行。第二次会导入第一次的初态，并启动本机固定回包服务。服务只监听回环地址，无外部模型费用。

```powershell
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-create
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-flight -From founding-create
```

每次使用未占用的运行名。证据写入 `work/<运行名>/founding-result.json`。夹具经原版飞行控制和物理推进玩家位置。固定回包只在玩家飞出营地加载范围后给出进食和移动计划。

### 单人生产

在「开始游戏 → 新建世界」选「生存」，点击「西部世界 · 单人生产」。世界中有一名 AI 和独立的本机观察玩家。AI 开局带一份面包和一把石斧，知道原版随身 2×2 制造格中的木板、木棍和工作台配方。开局优先选择靠近原生树干的干燥地点。模型配置、冻结初态、飞行、保存和共享额度沿用西部世界入口。

角色从局部观察找树干，持斧砍伐后追踪实际掉落物，拾取原木，再把原料移到自己的制造格。模型可用一个独立任务步骤提交 `act_Craft`，参数为 `workspace: "personal"`、已知配方的 `result_value` 和 `prepare: true`。既有配方编排器检查本人已有材料、制造格和背包容量，展开为连续摆料和制作步骤。该步骤使用零重试，不带分支或物品绑定；`count` 可省略，一批产量由配方决定。手动摆料后提交制造仍受支持。原版游戏核对射线、距离、库存和配方，扣除耐久和材料，产物进入背包。展开后的原子步骤及进度、制造格和进行中的砍伐随存档恢复。

单人实机夹具只预置一块可见的原版树干和可走地面。角色开局没有原木、木板或成品。固定回包版会在砍伐中用普通存档重开同一世界。真实模型版使用本机配置的凭证，预检上限为 0.03 美元估算，按现有 Luna 夹具单价计。

```powershell
pwsh -NoProfile -File game/scripts/verification/Run-SoloProductionSmoke.ps1 -Run solo-production-check -ReloadDuringDig
pwsh -NoProfile -File game/scripts/verification/Run-SoloProductionSmoke.ps1 -Run solo-production-live -Live
```

### 双人合作生产验证

夹具在同一个原版生存世界绑定两个生产角色，分别给杉 3 块木板、给禾 1 块木板，并为他们设定制作工作台的共同目标。两个角色各自请求真实模型。验收记录双方实际听到的发言、接收方接受后的转移事件、两人背包的数量变化，以及接收方使用原版配方制作的工作台。测试使用本机凭证，运行额度按夹具单价估算为 0.03 美元。

```powershell
pwsh -NoProfile -File game/scripts/verification/Run-CooperationSmoke.ps1 -Run cooperation-live
pwsh -NoProfile -File game/scripts/verification/Run-CooperationSmoke.ps1 -Run cooperation-gather-live -Gather
pwsh -NoProfile -File game/scripts/verification/Run-CooperationSmoke.ps1 -Run cooperation-mechanics -Mechanics
pwsh -NoProfile -File game/scripts/verification/Run-CooperationSmoke.ps1 -Run cooperation-plans-restore -Gather -ReloadDuringCooperation
```

加 `-Gather` 时，两人开局没有原木、木板或成品，只有杉带一把石斧。夹具在两人附近放一块原版橡木树干作为可采资源，给两人共同的工作台目标和配方，由模型商量分工。结果追踪树干坐标、地面掉落、拾取者、材料交接前后的两人库存，以及接收材料后制作并入包的工作台。采集场景的运行额度按夹具单价估算为 0.05 美元。

生产角色的局部观察为实际看见的人物提供 `bearing` 和 `horizontalDistance`，可用于原有相对移动工具走近交接。`supportsItemOffers` 标明该对象是否支持接收物品提议，便于区分本机观察玩家和有效交接对象，不包含对方的库存内容。操作提示说明如何引用实际收到的消息记录自己的分工或交付承诺，并在完成或改动后解除。承诺由模型选择记录。夹具要求接收材料的人制作工作台，单人包办或只交付成品时按未通过记录。

`-Mechanics` 不调用模型，检查可见人物的移动方向和交接能力、同一有效提议重发后旧编号仍可接受、重复接受只结算一次、修改数量后替换提议、拒绝后保留原库存，以及自动摆料制作在缺料时拒绝、中途归档恢复后连续完成。不能与真实模型测试同时启动游戏。

结果写入 `work/<运行名>/cooperation-result.json`。同一发送人对同一接收人、来源格、物品值和数量的有效提议重发时复用原编号，不重复发送消息或延长有效期。改变条款会替换发送人的旧提议。世界调度检查点同时保存仍有效的提议及原编号、人物消息与物品库存，恢复后沿用原有效期限。已经结算的物品归属随原版库存保存。

发送人的 `production.outgoingOffers` 列出本人尚有效的待回应提议，包含接收者引用、物品、数量和剩余有效时间，供后续决定参考。发出提议后材料仍由发送人持有，可由本人决定继续使用；接收时重新核对实际库存。

`-ReloadDuringCooperation` 在首次出现真实交接提议时请求动作边界归档，停止派发并等在途请求落账，导入该 `.scworld` 后关闭第一进程。第二进程载入归档并续用同一账本，在推进世界前核对模拟时点、个人计划、事件等待和近期过程。最终合并保存点之前与恢复之后的证据，核对砍伐、拾取、材料交接各结算一次，原木加工和工作台制作各成功一批。检查点结果在 `cooperation-checkpoint.json`，恢复元数据在 `cooperation-resume.json`。

### 西部世界普通存档恢复

正常退出到菜单或关闭窗口，重新启动时沿用原来的模型端点、模型、协议和计价配置，再从世界列表打开同一个世界。游戏加载营地和 AI 活动区块后，从保存的模拟时点恢复人物认知和任务。保留 `doc/Westworld/<运行标识>/cognition/` 中原有的账本。

原生 `Project.xml` 将人物的世界状态与任务游标一同写入。已结算的步骤从原游标越过。进行中的移动和转向使用保存的目标与剩余时限，等待接着计时，讲话从尚未说出的片段继续。匹配的已保存回包可以复用，结果不明的旧请求保留费用预留，角色之后可基于当前现场重新思考。

旧版普通存档已有的世界与库存照常恢复，首次用新版打开时，AI 基于这个存档的现场开始决策，已缺失的任务进度无法补回。模型配置或账本与存档不匹配时，世界会暂停并提示检查。强制终止与任意时点的地形崩溃一致性另见[异步检查点与跨进程恢复](#异步检查点与跨进程恢复)。

用前节生成的初态做实机回归。两次使用同一个运行名，启动器等待正常关窗，再打开同一目录中的世界。模型由本机固定回包服务替代。

```powershell
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-save -From founding-create -SaveForResume
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-save -Resume
```

### 跨实验额度与自动暂停

同一游戏数据目录下的西部世界共用额度。启动启用模型的游戏前，设置 `WENMING_FOUNDING_BUDGET_NANO_USD` 为累计总额，本轮 200 美元填 `200000000000`。再设置 `WENMING_FOUNDING_INPUT_NANO_USD` 和 `WENMING_FOUNDING_OUTPUT_NANO_USD`，分别为实际模型每 token 的纳美元单价。首次建立共享账时，存储上限默认 15,000,000,000 字节，可用 `WENMING_FOUNDING_STORAGE_LIMIT_BYTES` 指定。后续启动沿用已记录的上限，可显式提高。

每个实验保留自己的 `cognition/ledger.json`。共享的 `doc/Westworld/quota-account.json` 保留所有已登记实验的实际费用、在途预留及用量未知的负债。网络派发前先确认本实验账本和共享账落盘。同一数据目录同一时间由一个实验运行进程占用。读档、新开世界和清理旧世界文件都不会返还已记账费用。迁移数据目录时同时保留共享账本和各实验账本。

容量统计覆盖本机 `doc/Worlds/`、`doc/Westworld/`、`Bugs/`、`doc/Exports/` 和游戏的 `WorldUpload.tmp`，包括其中的世界、区域文件、日志、账本、归档、备份和临时文件。运行中每秒测量占用和实际磁盘余量，发布动作间归档前再检查。为待写账本、在途回包、原生保存及已修改区块留出余量。手动放到这些目录之外的副本由使用者管理。

下一次调用超出累计额度，且已准入请求结清后仍无法容纳，或预计写入将挤占存档余量时，游戏停住模拟时钟并自动保存。已在途的回包继续记账，候选动作等世界继续时处理。只读面板的「模型」页显示原因、保存状态、跨实验费用和存储余量。发生实际写入失败时保持暂停，账本或暂停存档写入成功后才允许继续。

要追加额度，在游戏数据目录下编辑或新建 `doc/Westworld/quota-limits.json`。填写新的**累计总上限**，只填要提高的项即可。以下例子把总费用提到 250 美元、总存储提到 20 GB。

```json
{"feeNanoUsd": 250000000000, "storageBytes": 20000000000}
```

游戏暂停时会读取该文件。额度和磁盘可用空间足够后，从保存的模拟时点继续，原任务和费用保留。追加存储上限后仍须有足够的实际磁盘空间。关窗再打开同一个世界也会保留暂停状态，直到条件满足。

固定回包回归从前节生成的初态开始。使用新运行名进行两个实验的累计费用、同进程追加、磁盘暂停和跨进程续跑验证。

```powershell
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-quota -From founding-create -Quota
pwsh -NoProfile -File game/scripts/verification/Run-FoundingWorldSmoke.ps1 -Run founding-quota -QuotaResume
```

## 实时世界面板

Windows 构建完成后，从仓库根目录启动游戏：

```powershell
$env:WENMING_PANEL_PORT = '18760'
dotnet run --project game/Survivalcraft.Windows/Survivalcraft.Windows.csproj --configuration Release --no-build
```

进入一个世界后，打开 [本机观察面板](http://127.0.0.1:18760/)。端口只监听本机。普通存档可看世界和玩家实体。已有全局认知调度的世界还会显示注册角色、请求和费用。用新运行名执行 `game/scripts/verification/Run-GlobalCognitionSmoke.ps1 -Run panel-check -Mode observe-ahead -PanelPort 18760`，可以在固定回包夹具运行时观察 50 人。夹具依赖下文的本机模拟服务，结束后会退出游戏。

接口 `GET /api/snapshot` 提供同一游戏线程上采集的世界和人物状态，以及近期内存事件。数据来源与容量见[面板设计](../design/AI监控面板信息与交互设计.md#14-刷新断线与一致性)。关闭页面只结束浏览器读取，世界仍由游戏运行。端口启动失败时检查 `Bugs/Game.log` 中的 `World panel could not start` 和端口占用。

观察觅食者对话时，人物可在任务中向附近发言。调度只接受无指定对象、无自动重试、无最低送达数的发言步骤，以便在动作边界恢复任务。游戏逐段判断实际听众，听到的消息可触发角色复查。模型候选里的台词要等到游戏实际执行后才进入对话页。

使用「对话」和「事件」查看竖排信息流。滚动查看旧记录时，面板会保留当前画面。跟随和筛选方式见[对话与事件的显示](../design/AI监控面板信息与交互设计.md#实时对话记录)。

## 修改后的检查

当前仓库没有独立的自动化测试工程。上游要求修改游戏代码后至少构建并启动进入存档；按改动范围补实际场景检查，不能用“无编译错误”替代运行验证。

Windows 实机验证一次只运行一个游戏实例。全局认知夹具默认在同一世界内连续执行常规场景，跨进程恢复另行验证。人物模型和全局认知的 PowerShell 7.4+ 夹具共用[启动与退出脚本](../../game/scripts/verification/Invoke-GameSmoke.ps1)，已有游戏实例时会拒绝另开游戏。

1. 构建目标 Windows 项目，记录错误和警告。进入新建的生存世界，确认生成、加载、角色出生与日志正常。
2. 若修改行动、身体或物品，在测试世界执行相关操作，观察实际位置、生命/体力、库存或地形变化，核对失败条件。
3. 若修改状态或存档，保存、退出并重新载入同一测试世界，核对新增字段、实体与资源结果。普通重载通过仍不能替代强制中断和重复效果检查。
4. 若修改界面、资源或模组，确认运行目录中加载的是本次构建产物，检查对应页面、文案、资源和钩子。
5. 更新受影响的代码导航或操作说明。新增运行证据时在当前状态记录源码版本、测试控制方式、结果和本地证据位置；原始记录保留在忽略目录。

AI 接入开始后，另按[测试与验收设计](../design/AI测试验收与演化证据设计.md)检查个人信息隔离、动作事实、恢复去重和预算边界。固定脚本完成场景只能证明受控路径；自主行为需要真实模型决定与游戏结果之间的记录。

纯文档修改检查本地链接、入口可达性和引用的代码位置，不要求重新运行游戏。

## 任务检查点与运行验证

在游戏更新线程上，宿主观察 `task_status` 处于 `waiting` 时调用 `ActorTools.SaveTaskCheckpoint(path)`，例如 `app:actor-task.scworld`。使用本机文件系统，父目录须已存在。该调用同步捕获世界与任务，适用于单个活动数据任务且后续步骤可从数据重建的情况。保存成功后通过原生导入加载归档，在第一次推进世界之前为同一实体创建新的 `AtomicActions` 和 `ActorTools`，再调用 `RestoreTaskCheckpoint()`。同一加载实例里每个任务只可恢复一次。该入口用于宿主，模型工具仍只接收角色自己的动作与任务数据。

可用 [发布夹具](../../game/scripts/verification/actor-task-smoke.js) 和 [恢复夹具](../../game/scripts/verification/actor-task-restore-smoke.js) 复现。分别在两个隔离的 Windows Release 运行目录，将相应夹具追加到原生 `init.js` 并用 `dotnet Survivalcraft.dll` 启动。第一个进程写出 `actor-task.scworld` 后退出，将归档复制到第二个目录再启动。两个目录各自的 `actor-task-result.json` 都应报告 `passed`。

## 人物认知运行器

### 个人计划、事件等待与近期过程

每次输入固定包含 `personalPlan`、`waitingFor` 和最多 16 条 `recentProcess`。近期过程来自本人实际执行的动作结果、实际收到的消息、计划与等待的修改和被拒绝的决定。动作结果包含原任务与步骤标识、本人提交的参数、实际数量和失败原因，讲话按动作状态解释。已确认处理的对话仍可保留在近期过程内。

实际收听的讲话可带 `sourceName`、`sourceBearing` 和 `sourceHorizontalDistance`，提供接收时的说话者标识与声源方向，供人物转身或靠近。人物移动或转身后结合新的观察判断位置与交接距离。声音播放音量为零时，讲话仍生成听觉线索和送达事件。

模型用 `plan` 提出个人计划，也接受 `personalPlan` 作为更新字段别名，同一响应仅使用其中一个。`operation` 为 `create`、`revise`、`complete` 或 `cancel`。创建和修改带 `purpose`、`next`、`completion`、`source`，修改、完成和取消还需当前 `version`。来源沿用下文的认知证据规则，也可引用本人近期过程条目的 `id` 或其中保留的原消息 ID。计划有稳定标识和递增版本，记录本人意图、完成条件和修改原因；完成状态是本人判断，物理结果仍按库存及动作回执验收。活动计划存在时，改动 `goal` 需显式修改计划。

`wait` 的 `kind` 支持 `itemOffered`、`itemsTransferred`、`speech`，可用已观察到的 `person`、已知的 `offer`、`itemValue`、最少 `count` 限定条件，`timeout` 为 0.1–120 个模拟秒。可以随动作任务一起提交，或者空闲时用 `task: keep` 提交。等待期间抑制单纯定时复查；实际匹配消息、拒绝、部分交付、超时、任务失败和身体状态变化会唤醒本人，其他新收到的交流仍可引发思考。`wait: {kind: "cancel"}` 取消等待。计划、等待期限、消息标识、近期过程和已完成任务游标一起保存，旧存档缺失的新字段按空状态读取。

宿主创建 `ActorTools` 后可绑定 `new ActorCognition(tools, profile)`。在游戏更新线程调用 `PrepareTurn()`，它返回待决策的 JSON 字符串，或在暂无思考需要时返回空值。决定来源读取输入的 `id`、`reasons` 和已选数据块。动作参数沿用 `ActorTools.DescribeToolsJson()`。

宿主用 `CommitTurn(id, responseJson)` 提交决定。最小返回形如 `{"reason":"先等一下","task":"keep","reviewAfter":3}`。`reviewAfter` 使用 0.1–120 模拟秒，省略时为 10 秒。选择 `start` 或 `replace` 时给 `steps`，格式沿用 `submit_plan`；`cancel` 取消当前任务。可选字段有 `goal`、`remember`、`commitment`、`resolveCommitment`、`handled`、`plan` 和 `wait`。记述和承诺用 `{source,text}`，来源为本轮的 `observation`、`body`、存在时的 `task` 或 `taskOutcome`、本轮消息 ID，或仍保留在本人近期过程中的条目及原消息 ID。近期实际收到的人物及提议引用仍可供本人的动作使用，现场距离、库存和提议有效性由游戏重新检查。`handled` 确认处理指定消息。拒绝的候选可用原输入修正，拒绝原因也进入近期过程；任务或身体处境过期时由宿主重新取上下文。`AbandonTurn(id)` 释放该轮并保留未处理消息；`LastDecisionJson` 供宿主核对最近一次接受的输入和决定。

`SaveCheckpoint(path)` 和 `RestoreCheckpoint()` 使用原生 `.scworld` 归档。保存点位于认知轮之间、动作边界，任务需满足[动作间检查点条件](#任务检查点与运行验证)。有任务时与认知一并恢复；已送达的话、目标、承诺和记述保留，普通现场会话引用在读档后失效，生产角色的稳定人物引用保留。跨人物的有效提议由世界调度检查点一起恢复。恢复须在载入后第一次推进世界前完成。

[认知夹具](../../game/scripts/verification/actor-cognition-smoke.js)用于两个隔离的 Windows Release 目录。都将夹具追加到原生 `init.js` 后运行 `dotnet Survivalcraft.dll`。第一个目录运行固定决定并写出 `actor-cognition.scworld`。复制归档到第二个目录再启动，夹具识别它并执行恢复分支。两次检查 `actor-cognition-result.json` 中的结果。

## 大模型适配层

`ActorModelClient.FromEnvironment()` 从进程环境读取以下设置。官方直连默认使用 Responses API 和 `gpt-6-luna`。使用兼容中转时显式填写该中转的完整请求 URL 和模型标识。

| 变量 | 含义 |
| --- | --- |
| `WENMING_MODEL_API_KEY` | 当前端点的 API 密钥 |
| `WENMING_MODEL` | 模型 ID，默认 `gpt-6-luna` |
| `WENMING_MODEL_PROTOCOL` | `responses` 或 `chat-completions`，默认 `responses` |
| `WENMING_MODEL_ENDPOINT` | 完整请求 URL，Responses 默认 `https://api.openai.com/v1/responses`，Chat Completions 须显式配置 |

[ActorModelTurn](../../game/Survivalcraft/Westworld/Models/ActorModelTurn.cs) 在游戏线程用 `TryStart()` 冻结人物输入和该角色的动作协议。宿主暂停世界推进，在游戏线程调用 `Poll()` 取回结果并提交，随后恢复推进。等待期间只执行网络请求。过期回合及切换世界后的回复不会提交。一个回合最多派发一次，失败时返回有限错误码和可用的 `Retry-After`。宿主可用 `TurnId` 关联回合，需要放弃时调用 `AbandonTurn(id)`。成功结果返回模型、请求 ID 和服务端报告的输入及输出 token。

默认请求超时为 30 秒，最多生成 1,536 token，以容纳计划修订和等待条件，费用预留沿用同一上限计算。Responses 使用 JSON 对象模式并设置 `store:false`。兼容 Chat Completions 使用 `messages` 和 `max_completion_tokens`，要求返回常规单条文本响应。两种回复都走认知层的结构和动作校验。全局等待、预算和请求账本按[调度设计](../design/AI时间推进与调度设计.md)实现。

从仓库根目录构建后，可用下列命令在隔离世界发出一次官方真实请求。命令会在终端通过安全输入提示读取本次密钥，结果写入 `work/<Run>/actor-model-result.json`。

```powershell
& game/scripts/verification/Run-ActorModelSmoke.ps1 -Run model-official-check -Live
```

本机回归先启动 [模拟服务](../../game/scripts/verification/actor-model-mock.py)，再运行同一夹具。Responses 端点用 `http://127.0.0.1:18759/v1/responses`，兼容 Chat Completions 用 `http://127.0.0.1:18759/v1/chat/completions` 并传入 `-Protocol chat-completions`。限流和畸形回复分别使用 `/rate/responses` 配合 `-RateLimit`，以及 `/bad/responses` 配合 `-InvalidDecision`。

## 全局认知调度夹具

宿主创建 `WorldCognitionScheduler(source, directory, parallelism, budget, inputPrice, outputPrice, priceVersion)`，用 `Register(cognition, tools)` 登记最多 50 个角色，再调用 `StartObservation()`。并发可配置为 1–15。金额用整数纳美元，单价用每 token 的纳美元。运行目录保存独占账本 `ledger.json` 与最新 `observation.scworld`，应置于忽略目录。用 `StatusJson()` 查询状态，`SetPaused(bool)` 暂停和继续，`IncreaseBudget(total)` 提高本轮总额度。

世界和人物照常推进。任务提交时登记提前请求机会，任务结束时尝试交接。每人最多一个在途请求或待交接决定。15 并发时，空闲角色有 10 个名额，执行中的角色有 5 个。回包由游戏线程从有界队列取出，复查角色状态、位置、物品与目标。原任务失败、取消或被替换时丢弃后续候选。

请求账本由单个后台写入任务分批发布。发送意图和预留确认落盘后才发请求，返回的候选与用量一起按原尝试 ID 保存，确认落盘后才释放预留和采用决定。写入故障暂停运行。正常结束时调用 `StopObservationDispatch()`，等 `inFlight == 0` 且 `ledgerPending == false`。

### 异步检查点与跨进程恢复

首次派发前发布初始检查点，此后每隔 10 个模拟秒尝试保存，也可用 `RequestObservationCheckpoint()` 提前触发。保存时暂缓新的任务步骤，已开始的动作和有限重试继续到动作边界。游戏线程同步捕获原生世界、个人认知、活动任务游标与已完成步骤、待决策输入及请求 ID，并以原子替换发布校验后的归档。模型等待和账本写入继续使用后台任务。

重启时，用相同模型与计价配置加载 `observation.scworld`，在世界首次推进前绑定原实体并调用 `ResumeObservation()`。检查点与账本必须属于同一实验。检查点里仍待处理的请求若已在账本保存回包，直接按现有校验与任务交接规则复用，包括检查点之后才落盘的匹配回包。已完成的任务步骤及世界效果随归档恢复。检查点之后未保存的世界进展会回退，相关请求费用保留。观察发生在检查点之后且缺少匹配输入的回包只保留作账目与审计。

发送结果不明的在途请求转为未知负债，恢复后暂停相关角色的新请求，其他角色与已恢复的任务照常执行。`RecoverObservationLedgerAsync()` 仍可独立核对旧异步运行的费用账目。旧冻结批次运行的归档与账本按历史版本保留，现有调度器拒绝把它们作为异步运行载入。

从仓库根目录构建，在单独终端启动本机模拟服务，再使用新的 `-Run` 名称逐次运行。夹具仅使用一个游戏实例。下面两次启动沿用同一份 50 人觅食世界和账本，固定回包让已结算进食、待交接候选和在途发送同时出现在中断点。首轮发布报告后由启动器强杀进程，第二轮从复制的运行目录恢复，核对世界时间、实体、任务 ID、游标、库存、请求 ID 与费用。

```powershell
python game/scripts/verification/actor-model-mock.py
```

| 模式 | 验证范围 |
| --- | --- |

观察夹具用 `StartObservation(true)` 启用采样，通过 `ObservationMetricsJson()` 收集调度、账本与请求等待时间。首次等待从观察启动算起，提前请求等待从原任务提交算起，均截至实际派发。帧间隔报告 P95、P99、最大值和超过 50、100 毫秒的次数，观察后的结清不计入窗口。对照可用 `-ObservationBaselineRun <旧运行名>` 复用同依赖与资源的游戏程序集。

## 常见定位顺序

| 现象 | 首先检查 |
| --- | --- |
| `dotnet` 无法识别 | SDK 安装路径和当前终端的 `PATH`；修正环境后重新打开终端 |
| 恢复包失败 | `game/nuget.config`、网络与输出中的具体包错误 |
| 新代码没有生效 | `.props` 的源码纳入范围、实际运行的程序集目录与构建配置 |
| 启动或图形初始化失败 | `Bugs/Game.log`、输出依赖和显卡兼容；ANGLE 处理见[上游 Windows 说明](../../game/README.md) |
| 更新组件异常但游戏继续运行 | `SubsystemUpdate.Update` 对单个更新异常有吞掉的路径；检查断点与组件自己的日志 |
| 重载丢失新增状态 | 组件/子系统的模板注册、`Load` / `Save` 和调用保存时的世界目录 |

没有错误日志不等于动作成功；排查时同时对照游戏中的实际状态。
