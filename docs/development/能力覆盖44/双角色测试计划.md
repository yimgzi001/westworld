# 阶段44：单世界双角色生存协作最小真实测试计划

状态：源码只读审阅后的实施方案，尚未实现本场驱动、未运行本场游戏、未调用模型API。本计划独立于其他多人设计，不能当作实测通过报告。

## 目标和范围

验证同一实际游戏世界中的A、B两名外部角色，拥有各自身份、观察、库存和动作所有权，能把**新从世界获得的食物**交给同伴并由同伴真实食用。其次验证A有正在执行的动作时，B仍可独立工作。

第一场使用明确标注的人工近距离食物夹具，排除找食物随机性；不是自主寻路、自然生存或模型协作。不能把两独立世界的两个进程拼成“联机成功”。不增加云模型调用，不用NPC旁白模拟交换结果。

## 已有可复用实现

- `CapabilitySocialMatrix40`已经在一份`Project`中持有两名`ComponentPlayer`，分别构造`AtomicActions`、`ActorTools`、`NativeToolSession`。其42模式已经验证社交动作的同次事实、关联参数和动态菜单；可复用offer/accept/decline/expiry及停止排空方式。
- `Program.cs`的`matrix_social`路径在同一`GameManager.Project`添加两个`PlayerData { IsExternalActor=true }`，等待两个原生角色就绪，而不是启动两个世界。此路径不为他们创建`ToolAgentScenario`。
- `NativeActorSession`以一份Project绑定多个外部角色。对本场继续设`actionsEnabled:false`，仅给观察/兴趣区域使用，避免与每人的AtomicActions争抢物理控制权。
- `NativeToolSession`对每个ComponentPlayer只允许一个登记实例，并验证ActorTools绑定相同角色。每人的工具账本、SessionId、ActorId分别保持独立。
- `CapabilityFacts`、`SocialTaskFamily`、`NativeEatOfferFactory`、`ToolDecisionPrompt`提供当前事实到闭合schema的复用途径。本场应扩展现有双角色验证器，不能直接让原生Call绕开动态菜单后宣称接口覆盖。

## 最小实现边界

新增独立双角色场景类或社交场景局部扩展，保留旧social42回归入口，不把单人ToolAgentScenario复制两份并共用其全局状态。

每角色状态封装：

- 固定`ComponentPlayer + AtomicActions + NativeToolSession`。
- 自己的观察capture、菜单选择、记忆/近期回执、收到的社交事件。
- 自己的pending动作/任务ID、截止时间及最终回执。
- 自己的库存基线和食用统计。

协调层只推进场景状态机、收集公开证据与判定结果，不替任一角色提供另一人的私有库存；测试oracle可分别读取两个角色端口，用于总量守恒，但不得将oracle合并视图放入任一角色提示/菜单。

一次游戏更新推进两个独立状态机；不得用“A先跑完所有任务，再启动B”的全局等待伪装并发。两人的世界时钟与物理更新属于同一SubsystemUpdate。

## 场景脚本

### 0. 世界和身份基线

1. 一次性新世界中创建A、B，均`IsExternalActor=true`且已进入同一Project。
2. 记录共同world/run标识、seed、Project身份一致断言；记录两个不同的entity ID、PlayerIndex、SessionId、ActorId。确认双方GameWidget均为空。
3. 若出生在载具上，各自原生Dismount并等待本人终态；不可瞬间删载具替代。
4. 明确记录人工平地和两角色相邻摆位、移除出生阻碍等夹具变更。等待必要地形就绪，不扩充可见范围，不伪造目标引用。
5. 双方分别observe/read_inventory/read_self，保留出生物品。出生食物不计入本次新食物来源。

### 1. 新食物获取

1. 在A近处放置一份明确标注的CookedMeat世界掉落，记录来源ID、位置、value和count。它是人工世界资源，不是直接加进A背包，更不是狩猎/烹饪成果。
2. A用自己的当前observe找到真正pickable引用；经本人的当前动态菜单执行PickUp，校验原生终态及A库存新增1份对应物品。
3. B同期执行一个短Wait或姿态动作。记录双方动作开始/终态区间，证明各自owner可同时存在，B不因A动作被全局busy锁住。
4. 全程记录来源链：fixture drop → A pickup receipt/runId → A确切slot/value/count。若自动拾取已先发生，不冒认脚本PickUp成功，明确改记原生自动拾取或本次失败重设场景设计。

### 2. 真实食物共享

1. A用自己的当前观察获得B引用，Speak说明“把新取得的熟肉给你”；B的read_social验证实际收到的文本。定向说话不等于秘密私聊。
2. A用刚读到的slot/value/count执行OfferItem，记录offer之前和之后两人库存。**提出offer时不得已经转移物品**。
3. B仅使用自己read_social实际收到且未过期的offerReference执行RespondToOffer(accept=true)。不把A端的offer对象直接塞给B当收件凭据。
4. 验证A减少1、B增加1、合计数量守恒，且关联到同一offer与原生回执。重复接受作为单独负例，不能增加任何物品。

### 3. 同伴食用与并发

1. B重新读本人库存，用动态Eat菜单选其实际收到的食物槽和值，不沿用A的slot或旧value。
2. A开始一个1至2秒的原生Wait，B同时执行Eat；两个pending状态各绑定各自runId。证明B食用不终止A或替换A的任务。
3. B原生Eat成功后：收到的食物数量减少1；本人food数值上升（允许正常tick衰减，比较紧邻前后）；本人食用统计增加。A未食用且统计不变。
4. 结果报告为“人工世界新食物获取→跨角色交付→接收者实际食用闭环”，不称自然环境自主生存。

### 4. 隔离负例

所有负例明确标记，优先停在schema验证，不提交写入：

- B菜单不得接受仅A持有的slot/value配对或A的capture。
- 把A端inventoryReference用于B的read_storage，预期原生拒绝且双方库存不变；若此调用产生账本不确定状态，仅按既有本人只读状态和reconcile协议恢复，不盲重试。
- A、B对同一个世界实体的引用均从各自观察生成，不假定引用字符串可跨角色通用。
- 已消费/过期offer不可再次接受；B未实际收到offer则菜单不可开放RespondToOffer。
- 停止A任务不影响B的owner、request ID或库存。停止全场则必须逐人排空。

## 验收证据

至少记录：

- 唯一world标识与两个真实角色实体、同Project断言。
- 每次调用的actor/session/capture/request或run/task ID，真实公开观察/库存/收件回执。
- 每一步食物来源、库存增减与合计守恒；B食用前后food和统计。
- 双角色动作重叠区间、独立终态，不把“同时存在”冒充“并行执行”。
- 注入、摆位、人工地形等夹具标记；无模型API和token消耗，不声称模型决策。
- 两人都停止且无待执行动作/任务，再恢复夹具或卸载一次性世界。任何owner隔离失败或无法排空，结果失败，保留诊断，禁止继续改地形。

CPU/内存如采集，应记录同一个游戏进程、有效采样区间以及1人与2人对照的相同条件。外部角色没有GameWidget不意味着整个应用完全没有渲染，不能将零AI视口写成零GPU消耗。

## 真实多人构造限制

- 原版普通玩家同屏上限与外部角色上限不同：当前`SubsystemPlayers.MaxExternalActors=50`是源码容量，不是50人性能/稳定性证明；本场只证明2人。
- 当前是同进程同世界的外部角色接口，不是跨机TCP联机服务，不自动包含网络认证、多人服务器或分布式角色迁移。
- 同一个ComponentPlayer不能再建立第二套NativeToolSession或第二动作owner。现有注册生命周期通常到一次性世界卸载才结束，不复用已dispose的同一实体重绑。
- NativeActorSession.Bind要求同Project、真实已加入Project的外部角色。普通玩家、异世界实体或未就绪实体不可借壳进入。
- InterestCoordinator需要覆盖两人的区域并合并管理；不能只维持A的加载范围再让B离开后停止模拟。第一场保持近距离以排除区块卸载变量，后续才做分散行动。
- 社交视听、距离、offer期限、库存容量仍服从原生规则；“团队”并不授予全图信息或读取另一人背包权限。

## 后续而非本场承诺

第一场通过后，可把人工熟肉替换为可见动物狩猎、原料交付、烹饪再共享，或A采木/B制作的完整分工。每次都沿用同世界、各自owner、真实来源链和同帧动态菜单，不一次引入模型、远距离加载和全自动生存等多个新变量。
