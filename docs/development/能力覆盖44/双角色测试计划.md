# 阶段44：同世界双角色食物共享计划

状态：只读审阅后的设计，未实现/运行本场驱动，无模型API。不得当作双角色生存通过报告。

## 最小实现入口

新增独立`CapabilityCoopMatrix45 : IUpdateable, IDisposable`，沿用`matrix_social`创建两个`IsExternalActor=true`角色的路径；通过独立模式或环境开关选择新场景，保留旧social42回归。

复用`CapabilitySocialMatrix40`的双角色创建、原生社交、私有收件箱及停止排空；复用`CapabilityFacts`、`SocialTaskFamily`、`NativeEatOfferFactory`和`ToolDecisionPrompt`生成各自当前动态菜单。不直接复制两份单人`ToolAgentScenario`，也不把raw调用当菜单验收。

每人持有唯一`ComponentPlayer + AtomicActions + NativeToolSession`，以及自己的capture、库存、收件、菜单选择、pending run/task ID和截止时间。共用一个Project及世界时钟。`NativeActorSession(actionsEnabled:false)`只负责观察/兴趣区域，避免第二套物理控制者。

## 一场脚本

1. **身份基线**：断言两人同Project/同世界，entity ID、PlayerIndex、SessionId、ActorId不同；两人GameWidget为空。各自原生下船、等待就绪，记录人工平地和摆位，保留并排除出生食物。
2. **获取食物**：人工放一份CookedMeat世界掉落，不直接加进背包。A以本人当前观察引用执行PickUp，验证原生终态、库存新增及来源链。若已自动拾取，明确标注，不冒认脚本PickUp。
3. **交付**：A观察B、Speak、OfferItem；B从自己的read_social得到offerReference再Accept。提出offer时不应转移；接受后A减1、B加1，总数守恒。不得把A端offer对象当作B实际收件证据。
4. **食用与并行**：A开始1至2秒Wait，B刷新自己的库存和Eat菜单后食用收到的食物。验证两个owner/runId独立且执行区间重叠；B对应物品减1、food上升、食用统计增加，A统计不变。
5. **收尾**：逐人取消并验证动作/任务空闲，再卸载一次性世界。排空不确定则失败，禁止继续恢复地形。

结果只能称“人工世界食物获取→跨角色交付→接收者食用闭环”，不是自然环境自主生存、模型组织协作或跨机联机。

## 必须保留的负例和证据

- B菜单不得接受A专有的slot/value、capture或目标引用。B用A的inventoryReference执行只读storage负例应拒绝，双方库存不变；不确定账本按既有只读核验/reconcile流程处理，不盲重试。
- 重放已接受/过期offer不增加物品。没有实际收件不得开放RespondToOffer。
- 日志包含共同world、每人session/actor/capture/runId、本人公开观察和库存、食物来源、交付守恒、食用前后及动作重叠区间。
- 跨人库存合计仅属于测试oracle，不把它放入任一角色提示或菜单。
- 人工地形、摆位、食物注入全部标记；固定脚本不记作模型决策，无API/token消耗。

## 已核实的限制

- `SubsystemPlayers.MaxExternalActors=50`是源码容量，不是50人性能/稳定证明；本场只验2人。
- `NativeActorSession.Bind`要求真实外部角色、同Project且实体已加入Project。`NativeToolSession`禁止同ComponentPlayer第二次登记；结束后卸载世界，不复用旧实体重绑。
- 当前是同进程同世界接口，不包括TCP服务器、网络鉴权或跨机迁移。
- 保留两个角色的InterestCoordinator区域；首场近距离，后续才测试分散加载。
- 无AI视口不等于整个游戏进程无渲染。资源比较要记录同进程、相同条件与有效采样窗口。
