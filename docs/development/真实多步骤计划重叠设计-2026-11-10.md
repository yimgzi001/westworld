# 真实多步骤计划的重叠设计（阶段34提案，未整合）

## 已核实的问题

`work/natural33-terra/tool-agent.jsonl` 的三个模型计划依次是单个 `act_Dig`、单个 `act_Dig`、`act_MoveTo + act_PickUp`。前两次不属于当前移动前序；第三次仍有一个未执行步骤，所以当前 `PrecedingExecution.CanPrefetch` 正确返回 `remaining_plan_steps`。该次移动途中自动拾取已满足目标，不能为了增加重叠数字再发一次不需要的模型请求，也不能把未执行的显式 PickUp 记为成功。

目前不建议删掉 `remainingSteps==0` 判断。直接删除会使新计划在旧计划尾部之前插队，或者把一个 MoveTo 的成功错误当成整个 MoveTo/PickUp 计划成功。不能要求模型只返回单步绕过此边界。

## 现有可复用代码

- `game/Survivalcraft/Westworld/Cognition/WorldCognitionScheduler.Observation.cs`：`ProcessObservation` 以 `PrecedingTask` 绑定请求；`SendObservationRequest` 发出前检查活动任务身份；`ApplyObservationSettlement` 暂存早到回复；`ProcessObservationTaskEvents` 在任务结束后交接。可以复用生命周期与事件结构，但“结束”本身不能代替当前宿主要求的成功、物理停稳和新观察复验。
- `WorldCognitionScheduler.ObservationLedger.cs`：`StageObservationLedger` 汇集不可变状态，`WriteObservationBatch` 后台写，`ConfirmObservationBatch` 回到权威线程确认，适合减少同步日志/序列化阻塞。不能把任何未完成审计写入宣称为已持久化。
- `experiments/scapi-tool-agent/PrecedingExecution.cs`：现有单次 run/receipt/session/actor 身份校验、失败锁存和实际状态准入应保留。
- `runtime/Westworld.Runtime.Core/AsyncDecisionHandoff.cs`：继续用唯一请求或候选槽，不另建第二控制器。
- `ToolOutcomeFeedback.cs`：只有真实终态才生成前后库存净变化，不证明物品来源。可作为后续重新决策事实，不能用于预报未来背包。

## 分层实施

### A. 先并行动作与非决策准备

游戏线程在动作运行时采集一次不可变公开观察、库存和实际动作身份。后台只做纯序列化、摘要、token/字节预算计算、日志批写，不调用游戏对象，不重新扫描世界，也不持有可变 Entity/Inventory。

准备产物必须带 session、actor、plan revision、observation ID、采样时刻与前序 run ID。它不授予执行权限。真正发请求前或派发前由权威线程确认身份、预算与所需新观察；动作完成、目标改变或资源引用失效时舍弃旧准备。不要通过复用旧快照省掉必要的新感知。

此步只减少主线程额外开销，不能宣称降低云端模型的12–21秒推理时间。需分别记录采样、纯投影、序列化、文件写入和模型等待耗时，避免把准备并行混称为模型与动作重叠。

### B. 有界计划尾部屏障

新增独立纯 `PlanContinuationFence`，不改工具策略。绑定一个原计划 revision 与至多4个步骤的原始名称/参数指纹。已经执行的前缀只记录真实结果；发出预取时明确给模型正在执行及尚未执行的原计划尾部，候选是“这段原计划真实完成以后”的备选，不是立刻替换剩余步骤。

每一步到实际派发时才绑定 receipt sequence 和真实 run ID；不能为未来步骤伪造运行身份。每一步必须按原顺序、原工具与参数执行，终态记录不能串到其他 run。尚未派发的步骤没有收据，也不能凭队列移除推断执行。

任一步失败、取消、身份替换、复验失败、未执行或计划 revision 改变，整个候选屏障失效。包括“MoveTo自动拾取后旧PickUp引用失效”：这是需要报告的新事实，不是自动认定原PickUp成功。若最终任务已经达成，可取消不再必要的候选，不再补模型调用。

所有绑定步骤实际成功、活动所有者释放、身体停稳以后，才进入原 `AsyncDecisionHandoff` 的 fresh observation / schema / native 校验。新观察与规划观察 ID 不同只是身份检查，不证明内容新鲜；采样时刻与权威线程负责真实新鲜性。候选不改变已执行或排队步骤。

仅当最终目标确实还需要下一段决策、剩余额度允许且预取槽为空时发请求。总4次/180秒、单次45秒与原deadline保持；超时、晚结果、取消后的回复只记审计不能派发。失败请求也消耗原额度。

### C. 非移动动作的后续扩展

单Dig可以异步思考，但必须另定义“动作确实在进行”的原生证据，不应要求身体位移，也不能通过无限走动掩盖等待。复用真实原生run身份与实际挖掘进度/目标状态；没有可用进度证据时先只做准备并行。

规划时尚未出现的掉落、未来库存、将制成的武器或熟食不能进入可执行候选。模型可以保留阶段目标，但新物品需要真正出现后的新观察。不要为了提前选择PickUp/Eat构造未来引用。

## 最小文件边界

- 独立纯 helper `PlanContinuationFence.cs` 与独立测试：步骤顺序、身份、真实终态、失效、期限，不引用游戏程序集。
- 后续宿主接线由 Program/Prefetch 所有者统一做，不与自然食物夹具并改。
- 准备/序列化并行单独组件，只接不可变JSON和绑定身份，游戏线程采样仍由宿主负责。
- 阶段34已实现独立 `PlanContinuationFence.cs` 纯契约及失败矩阵测试，但尚未接入宿主。计划级预取运行、Dig预取和后台准备仍未实现，不能计入现有模型重叠成果。

## 整体验收

1. 两步原计划（移动+真实可完成操作），模型回复早到；不能提前越过第二步，最终成功停稳后只派发一次候选。
2. 相同计划回复晚到但未过deadline；旧计划成功后等待，无重复派发。
3. 第二步失败/取消/旧引用失效/实际run替换；候选全部弃置，真实失败仍保留。
4. 自动拾取令目标达成、显式PickUp未执行；诚实记未执行，不补造收据，不为重叠指标增加API请求。
5. 输入未来库存或未知资源引用；必须拒绝，即使原计划“通常会获得”该物品。
6. 模型正在推理时总预算或用户停止；取消后排空，晚回复不执行。
7. 主线程准备开销与原生动作、模型时间分别采样，报告实际覆盖和样本缺口。不把规则驱动对照称为模型自主结果。
