## 新增机制与准确边界

1. 任务开始/结束事件排队；同一角色可以在现有任务运行期间预请求下一任务。
2. 提前回包先结算、缓存在内存，只有原任务 ID 一致且成功后才允许交接；失败、取消、任务替换和现场变化会使候选失效。
3. 后台单写入任务批量发布账本。发送意图确认落盘后才派发，结算确认落盘后才安装决定。这是源码设计；本批离线测试未启动世界，因此没有实测这两条实时派发顺序。
4. `RecoverObservationLedgerAsync` 只恢复费用历史，将未知发送结果保留为负债，不重新派发。它不是世界/角色/进行中任务或缓冲决定的恢复入口。
5. 此处预请求是后续任务交接，不是角色遇险时自动抢占、打断和替换当前任务。

## 真实 Player 接入前的必要适配

### 分离异步能力策略与检查点可恢复策略

`IsAvailableCohortTool` 对完整 Player 仍走 `IsCohortTool`，名单没有 MoveTo、FaceTowards、PickUp、Dig。不能仅调用 StartObservation 就称接通完整自然觅食；也不能换成简化 Forager 模板绕过。

应明确区分：当前异步可执行动作、可预请求交接动作、可跨进程检查点恢复动作。每项分别声明执行时局部重验与失败语义。PickUp 重验目前假定 `food_value`，不能直接套用通用 reference 版本。

### 保护活跃任务引用

Lookahead 的 PrepareTurn 会执行 CognitiveObservation，后者 Capture 会重建 live 引用表。正在 MoveTo(reference)→Dig(reference) 的计划可能因第二次观察丢掉尚待执行步骤引用。

启用前应在捕获观察之前阻止活跃引用型计划的 lookahead，或设计有上限的活跃引用保留及现场感知重验。不能把旧引用变成全知查询，也不能先清表再试图撤销。当前本批没有擅自修改这部分。

### 上下文与过期

完整 Player 的初始和纯 nextTask 回合未必包含库存，因为 needsInventory 只覆盖简化营养组件或 social/taskEnded/review。应为 initial/nextTask 补齐自身库存上下文。

相对 MoveTo/FaceTowards 的回包重验在位移超过 0.4 米或朝向点积低于 0.98 时拒绝。运动期间提前规划后续相对运动可能大量失效，不能把请求重叠率等同于有效任务吞吐率。

## 下一批一次性原生验收建议

在隔离云世界、完整 Player 和独立活动中心下执行一个统一场景组，使用可控延迟的本地决策源，禁止付费网络调用：

- 同一角色在自身请求未返回期间实际移动；记录 actor/task/request ID 和位置证据。
- 提前回包不抢占；原任务成功后才交接；失败、取消、替换、死亡后不安装。
- 相对姿态变化与资源变化拒绝旧候选；消耗型动作不重复执行。
- 引用型计划没有因辅助观察被破坏。
- 发送意图写失败时调用数为零；写确认前不调用；结算写确认前不安装。
- 排空、Dispose、立即重开和进程终止分别验证；未知费用不清零、未知尝试不自动重发。
- 多角色预算与排队公平性；本地模型标注真实 token/时间/RSS，不能将模拟 nano-USD 价格当真实费用。
